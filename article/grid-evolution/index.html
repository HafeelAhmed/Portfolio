Personal project
Grid Evolution

All entities exist within a 2D environment. There are no instructions for these entities about what to eat or how to avoid threats. Those with the most successful brains are used as a template for the next generation which then undergoes change. Within a couple of hundred episodes the entities can then teach themselves.

Where the idea came from

I wanted to see how a life with only one purpose, staying alive, would behave if it had its own neural network and nobody told it what to do. Nothing is scripted. Each Life has a small brain and a few rules about energy and food, and selection keeps whatever works.

I also wanted the system to be independent of any rendering framework. raylib only draws the world, and the simulation itself doesn't know it exists. If I want to use the same system inside Unreal, I should be able to drop it in and put Unreal on top instead. I've since done exactly that in Life Simulator.

The rules

The world is a grid, and each cell holds at most one food item, Life or Destroyer. Every tick, each entity gets one action.

Life

The creatures that learn

Each life can see a 5x5 square. The 123-16-16-8 neural network then chooses for a life to either pause, go in one of 4 directions, attack and/or eat. Energy is lost each tick. Attacking also uses energy and has a time before it can be done again. Once a life has eaten 5 food items it then produces offspring which has a possibly mutated version of its brain.

Destroyer

The threat

Destroyers have no brain. Each one runs a simple state machine that walks 5 to 8 cells, attacks a few times and starts again. Their energy never drains, so only Lives can kill them, and doing so earns a big fitness bonus.

Episode

Selection

When every Life is dead, the episode ends. The next one starts from the 10 best distinct brains, with 80% of the new Lives getting mutated copies and 20% getting exact copies. Fitness is ticks survived, plus bonuses for food, children and kills, minus penalties for idling.

Why neuroevolution

Gradient based reinforcement learning relies on a differentiable environment and training process. The neuroevolutionary approach only requires an end-of-life score. This allowed me to design, and even code, both the neural network and the forward pass from first principles, without using any ML libraries.

As well as allowing me to define a suitable fitness function (such as a Life’s lifespan, food intake and/or destruction of a Destroyer), the identical forward pass for each Life means that the whole population can be assessed in one ‘batch’. This enabled the use of a GPU as a backend for processing.

How the code is structured

The simulation is a library with no rendering dependency, so it can be reused in Unreal or anywhere else. The raylib GUI, a headless trainer and the test runner all link against it. If simulation code ever called raylib, the headless build would fail to link, so the linker itself keeps the two apart.

01

Data-oriented entities

There are only three kinds of thing, so instead of a full ECS or a virtual update() per object, each archetype is a plain struct in a dense vector, and behaviour lives in systems that run in a fixed order each tick. The data stays cache friendly, and I can test each rule on a small world built by hand.

02

Two-phase death

An attack can kill a Life that hasn't acted yet this tick, while other systems still hold references into the vector. Dead Lives are only flagged during the tick and erased once at the end, so no reference is invalidated mid-loop.

03

No exceptions

Unreal builds with exceptions disabled, so I did the same here. Anything that can fail (config parsing, model files, OpenCL) returns a [[nodiscard]] Result<T>, so ignoring an error is a compiler warning.

04

Deterministic runs

I wrote my own PCG32 random generator and distributions, because the standard library's distributions can differ between compilers. The same seed and config always replay the same run, and there are tests for that.

05

Events instead of polling

The UI needs to know when an episode ends, but the simulation must not depend on the UI. The simulation exposes events, and subscribing returns an RAII handle that unsubscribes in its destructor, much like delegates in Unreal.

Getting them to actually learn

The first versions barely learned anything. Most of the work on this project was figuring out why.

The first problem was the number of actions. I started with 13 actions (wait, plus move, attack and eat in each direction). Cutting it to 7 by making attack and eat non-directional took the best fitness from 1,094 after 1,500 episodes to 3,150 after 1,000.

The mutations were also too big. With a mutation strength of 0.3, the saved "best" brain did no better than random ones on new seeds. The first-layer weights were around 0.09, so every mutation scrambled the network. I swept 12 settings and settled on 0.05.

The last problem was Lives that just stood still. A fitness penalty for waiting stopped them wiggling back and forth, but they still idled 82 to 97% of the time. I wrote a diagnostic that logged every action, and it showed most "idle" ticks were actually failed actions: walking into a wall, or into food, which blocked movement like a wall. Three changes fixed it: walking into food now eats it, idling costs real energy, and each episode is seeded from the top 10 brains instead of one lucky individual.

Moving the brains to the GPU

Every tick, the simulation gathers all sensor inputs into one matrix and runs the whole population's networks in a single call behind a compute-backend interface. That made it possible to add an OpenCL backend next to the CPU one and switch between them in the config.

The first GPU version was slower than the CPU at every size: 7 ticks/s against 15 at 8,000 Lives. Because Lives are born and die every tick, I was re-uploading every genome every tick. The fix was a slot cache on the GPU: each genome gets a stable ID, only new ones are uploaded, and each tick only the slot indices are sent.

At the default size the CPU still wins because of launch and transfer latency. At scale the GPU is up to 7× faster, and its results match the CPU bit for bit.

Testing

The project has its own small test runner and 76 unit tests covering the network, evolution, combat and energy rules, config and model files, determinism and the GPU backend. It builds with zero warnings under -Wall -Wextra -Wpedantic -Wshadow.

You can save the best brain at any point and load it again later, either in the GUI or in the headless trainer.
